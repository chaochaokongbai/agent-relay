# 纯聊天客户端（paste-only）接入指南
## 一、什么是 paste-only 客户端？为什么它也能参与接力
### 1. 什么是 paste-only 客户端
paste-only（纯聊天型）客户端，指的是**没有 MCP 工具调用能力、没有直接读写本地文件能力**的 AI 聊天产品，典型代表就是豆包网页/客户端、ChatGPT 网页版等。你只能在聊天框里和它对话，它没法直接碰你电脑上的项目文件，也没法自己跑命令。

### 2. 为什么它也能参与接力
agent-relay 的核心是「跨会话接力干活」，不是所有模型都要有文件能力。我们设计了**粘贴协议（paste protocol）**，让「人」当中间的传输纽带：把项目上下文贴给聊天模型，模型输出结果，人再把结果抄回项目里，交给有文件能力的一端验证落地。

一句话：没有 MCP/文件能力不是出局理由，只是干活方式变成「你传我、我输出、你再抄回去」，一样能完整参与接力流程。

## 二、核心：粘贴协议（paste protocol）是什么
粘贴协议是一套固定的格式与流程，让纯聊天客户端也能标准化地参与接力。核心规则只有两条：
1. **输入靠粘贴**：项目的任务、上下文、历史交接记录，都通过 `relay paste` 命令生成一段完整的粘贴模板，由你整段复制贴进聊天框。
2. **输出靠抄回**：模型给出的结果（交接备注 / 回执 JSON），由你复制粘贴回项目对应的位置，再交给直连端执行验证和落地。

全程模型不需要任何文件权限，所有读写操作都由你和直连型客户端完成，安全可控。

## 三、完整操作流程（用户视角分步走）
### 第 1 步：告诉 relay 你要用纯聊天客户端接入
在项目目录下打开终端，执行：
```
relay connect --client doubao
```
这一步的作用是告知 relay：当前接入的是豆包这类纯聊天客户端，走粘贴协议流程，后续用 `relay paste` 输出粘贴模板。

### 第 2 步：生成粘贴模板，贴进聊天框
执行命令生成当前任务的完整上下文模板：
```
relay paste
```
命令会输出一段完整的「粘贴模板」，里面包含了：任务板、最近交接记录、决策记录、给下一个模型的指令。
👉 **你要做的：把这一整段内容全部复制，直接粘贴到豆包的聊天输入框里，发送。**

> 注意：不要删减内容，聊天端看不到你的仓库，全靠这段模板获取全部上下文。

### 第 3 步：等待豆包输出结果
豆包读完上下文后，会输出两部分内容：
1. 任务的具体答复（分析、方案、文档内容等）
2. 末尾固定格式的**交接备注**，如果涉及文件修改，还会输出**回执 JSON**

### 第 4 步：把结果抄回项目
分两种情况：
#### 情况 A：只有交接备注（纯讨论、无文件修改）
把豆包末尾的「交接备注」整段复制，粘贴到项目里的 `.relay/handoff.md` 文件中，完成本次接力交接。

#### 情况 B：包含回执 JSON（有文件修改/产出）
把豆包输出的完整回执 JSON（连同 json 围栏）复制，在项目里保存为 `receipt.json` 文件，然后交给有文件能力的直连端执行验证：
```
relay verify receipt.json --test "npm test"
```
验证门会做三件事：
1. 检查格式、破坏性写入守卫、敏感路径守卫
2. 把修改应用到项目临时副本里
3. 跑测试命令
✅ 测试通过（退出码 0）：修改正式落地到项目
❌ 测试失败：打回修改，不会影响真实代码库

### 第 5 步：接力继续
验证通过后，下一个人/模型就可以接着 `relay paste` 继续往下干了。

## 四、完整走查示例：豆包写这篇指南
我们就用「撰写本接入指南」这件事，走一遍完整流程，帮你直观理解。

### 1. 发起任务，生成粘贴模板
项目负责人在终端执行：
```
relay connect --client doubao
relay paste
```
得到一段粘贴模板，里面写着：
- 任务：撰写 docs/PASTE-CLIENT-GUIDE.md，面向新手的纯聊天客户端接入指南
- 背景：现有文档都假设客户端有 MCP，缺少 paste-only 专属指南
- 要求：中文、大白话、覆盖流程/示例/对比/坑点

### 2. 粘贴给豆包
把整段模板复制，贴进豆包聊天框发送。

### 3. 豆包输出结果
豆包读完后，先给出指南内容，末尾附上交接备注，再输出完整的回执 JSON（包含这篇指南的全文）。

### 4. 抄回项目并验证
你把回执 JSON 保存为项目里的 `receipt.json`，然后执行：
```
relay verify receipt.json --test "npm test"
```
验证门检查：
- transport 是 paste，跳过存活检查
- 检查 changes 数组格式合法
- 检查新建文件（docs/PASTE-CLIENT-GUIDE.md 是新建，跳过大小守卫）
- 复制项目到临时目录，应用修改，跑测试
- 测试通过，正式写入真实项目

### 5. 完成交接
把交接备注更新到 `.relay/handoff.md`，本次接力完成。

## 五、直连型 vs paste-only 型 能力对比
| 维度 | 直连型客户端（Qoder、WorkBuddy 等） | paste-only 纯聊天型（豆包、ChatGPT 网页版） |
|------|--------------------------------------|----------------------------------------------|
| MCP 工具调用 | 有 | 无 |
| 直接读写项目文件 | 能 | 不能，必须由用户抄录 |
| 自己跑命令/测试 | 能 | 不能，由直连端执行验证 |
| 接入方式 | 直接连接 relay | 通过粘贴协议，用户当传输中介 |
| 存活检查 | 需要校验 tool_call_count | 跳过，transport 设为 paste 即可 |
| 适合场景 | 编码、调试、批量修改文件 | 方案设计、文档撰写、代码评审、思路梳理 |

## 六、常见坑与注意事项
### 1. 聊天端改不了文件，必须输出完整文件全文
豆包没法直接修改你本地的文件，所以回执 JSON 里的 `content` **必须是修改后的完整文件全文**，不能只写 diff 片段、不能只写新增的几行。验证门是用全文覆盖写入的，只写片段会把原文件其他内容清空。

> 反面教材：原文件 100 行，只返回新增的 10 行 → 应用后文件只剩 10 行，属于破坏性写入。

### 2. 回执里 transport 必须填 "paste"
纯聊天客户端的回执，`transport` 字段**必须写 "paste"**，这样验证门才会跳过存活检查（因为聊天端没有工具调用计数）。填错会导致存活检查不通过。

### 3. 提示词要完整粘贴，不要删减
聊天端看不到你的仓库，所有上下文都来自粘贴模板。删减内容会导致模型信息不全，产出错误结果。

### 4. 有分歧/歧义，交给用户裁决
如果任务描述有模糊、方案有分歧、需要做取舍，不要自己拍板，在交接备注里标明「需用户裁决」，由项目方决定。

### 5. 不要相信聊天端的「我已经改好了」
纯聊天客户端没有文件能力，它说“改完了”只是输出了内容，**不会真的修改你电脑上的文件**，必须由你抄回并执行 `relay verify` 才会真正落地。

### 6. 验证门会拦破坏性写入，放心提交
不用担心写错搞坏项目：验证门会先在临时副本里试应用、跑测试，有问题直接打回，不会碰真实代码库。但也要尽量输出完整内容，避免触发破坏性写入守卫。

## 七、写在最后
paste-only 模式是 agent-relay 里门槛最低的参与方式——你不需要装任何插件、不需要给模型文件权限，只要会复制粘贴，就能让豆包这类纯聊天模型参与到项目接力里。

它适合做思路类、文档类、评审类工作，把重脑力活交给聊天模型，把落地执行交给直连型客户端，各司其职，安全高效。
